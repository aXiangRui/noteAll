# M2 实测记录：草稿提示词的第一次真机验证

> 2026-10-26，`deepseek-chat`，`max_tokens=256`，`temperature=0.2`。
> 工具：`dist\llm_smoke_v2.exe --draft "..."`（就是 M2 要走的那条链路）。

## 三条样本

| # | 原文 | kind | summary | tags | 耗时 |
|---|---|---|---|---|---|
| 1 | 明天下午三点跟老张开会讨论排期 | `event` ✅ | 明天下午三点与老张开会讨论排期 | 会议, 排期, 老张 | 739 ms |
| 2 | 读到一篇文章说 C++ 的 expected 比异常好 | `note` ✅ | 读到文章称C++的expected优于异常 | C++, expected, 异常处理, 阅读 | 971 ms |
| 3 | 记得周五前把周报发出去 | `todo` ✅ | 周五前发出周报 | 周报, 截止日期, 待办 | 1071 ms |

三条都通过了白名单校验（summary 非空、tags 是字符串数组、kind 在四值之内），
JSON 也都没带代码块围栏。

## 结论

**提示词可用，不用大改。** 三个 kind 全对，说明"event / note / todo / thought"这四个
概念对模型是清楚的，不需要写更多例子。

**两个小瑕疵，值得在提示词里补一句：**

1. 第 3 条把 `待办` 放进了 tags —— 和 `kind=todo` 重复，是废话。
   → 规则加一句：**tags 不要重复 kind 的含义，也不要用「工作 / 生活」这类空泛词**。
2. 第 2 条的 `阅读` 偏泛（几乎任何读到的内容都能打）。
   → 同上一条能一起解决。

**summary 偏"复述"**：第 1 条几乎等于原文。短句本来就压不出多少信息，
可以接受；等真的变吵了再调（比如限 20 字以内）。

## 延迟：影响草稿队列的预算

实测单条 **0.7 – 1.1 秒**（含网络往返）。所以：

- 之前设想的"命令收尾最多 3 条 / 1.5 秒"**不现实** —— 3 条要 2–3 秒；
- 改成 **最多 2 条 / 2.5 秒**，或者机会式 drain 只补 1 条，
  批量补历史交给显式的 `note draft --all`（那次本来就要等）。

## 成本

每次请求输出 ~90–120 字符，`max_tokens=256` 上限根本用不满。
按 DeepSeek 的价格，一条草稿的成本可以忽略；瓶颈是**延迟**不是钱。

## 下一步（接线顺序）
