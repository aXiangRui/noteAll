# 项目自评标准（Rubric）

> 用途：给这个项目的**当前状态**打分，并且能**反复打分**——每个里程碑结束时重跑一遍，
> 看分数往哪走、哪一维拖后腿。
>
> 核心规则只有一条：**每一维的分数必须附一条"可复现的证据"**（一条命令、一个文件行号、
> 一次实测输出）。**拿不出证据的维度，按 5 分封顶。** 没有这条，分数就会变成自我安慰。
>
> 首次评分：2026-10-15　｜　仓库：<https://github.com/aXiangRui/noteAll>

---

## 1. 维度与权重

权重按"做一个自己能天天用的 C++ 学习项目"这个目标定，不是均分：

| 维度 | 权重 | 为什么是这个权重 |
|---|---|---|
| 设计与架构 | 20% | 反复重写是个人项目的头号杀手，这一维最难事后补 |
| 实现正确性 / 健壮性 | 20% | 数据会坏、且**坏了不报错**等于项目死刑 |
| 测试 | 15% | 是上面两项的保险，不是装饰品 |
| 文档 | 15% | 学习项目的主要产出，也是三个月后唯一的记忆载体 |
| 工程化 / 版本控制 | 10% | 决定"改坏了能不能退"，是加速度问题 |
| 产品可用性 | 10% | 决定一周后是继续用还是弃坑 |
| 学习成效 | 10% | 学习项目的第一目标 |

> 权重可以改，但**改了要写在这里并注明原因**，否则历史分数不可比。

## 2. 评分锚点（每一档到底长什么样）

打分的争议通常不在"给几分"，而在"8 分和 9 分差在哪"。所以每维给三个锚点：

### 设计与架构（20%）

| 分 | 判据 |
|---|---|
| 6 | 分了层，但依赖方向靠自觉；数据模型有"不该出现的状态"能被构造出来 |
| 8 | **不变式成文并且被代码强制**（不可变字段、`optional` 表达"可能没有"、依赖方向写进硬约束）；新增一层不用改已有层 |
| 10 | 8 分 + **演化能力**：数据格式带版本号与兼容读路径、模块可独立测试、能说清"为什么不用另一种设计"（ADR 级记录） |

### 实现正确性 / 健壮性（20%）

| 分 | 判据 |
|---|---|
| 6 | 主路径正确、错误路径基本有处理；存在≤2 处"静默错数据"或资源泄漏 |
| 8 | **零静默错误**：所有失败都变成可观测信号（`expected`/warning/非零退出码）；IO 原子性、并发/重入、编码边界都有明确策略；契约（异常保证、线程安全、`noexcept`）写清楚 |
| 10 | 8 分 + 有**故障注入验证**（磁盘满、文件被占用、断电模拟、坏字节流）并且被自动测试覆盖 |

### 测试（15%）

| 分 | 判据 |
|---|---|
| 6 | 有一个模块测得不错，但**风险分布与实际风险不匹配**（最危险的层裸奔） |
| 8 | 按"静默失败 × 影响面"排序覆盖；边界值/非法值/回归用例齐全；测试可复现（无 `now()`、无随机无种子） |
| 10 | 8 分 + 自动化护栏：CI 每次 push 必跑、`-Werror`、属性测试（property-based）或 fuzz、覆盖率有下限 |

### 文档（15%）

| 分 | 判据 |
|---|---|
| 6 | 有 README/设计文档，但**与代码有已知漂移**，或含未经验证的断言 |
| 8 | 文档与代码同步；决策写"为什么"而不只写"是什么"；每条"实测"都是真跑过的；有验收清单 |
| 10 | 8 分 + 可执行文档（例子能跑通）、ADR 索引、新人（或三个月后的自己）能照文档把项目跑起来 |

### 工程化 / 版本控制（10%）

| 分 | 判据 |
|---|---|
| 6 | 有 git 且有远端，但缺 CI / 格式 / 静态分析 / 可重现配置 |
| 8 | 提交粒度合理、`.gitignore`/`.gitattributes` 妥当、构建一条命令、CI 跑测试、无杂物入库 |
| 10 | 8 分 + `CMakePresets` + 静态分析 + 依赖版本锁定 + 构建可重现 |

### 产品可用性（10%）

| 分 | 判据 |
|---|---|
| 6 | 主要流程能用，但**招牌能力没接线**或需要别扭操作 |
| 8 | 端到端闭环（输入 → 存储 → 展示 → 再取出），退出码/错误提示对人友好，日常无摩擦 |
| 10 | 8 分 + 用一周以上没有"数据/体验"事故，并且有明确的下一步演进点 |

### 学习成效（10%）

| 分 | 判据 |
|---|---|
| 6 | 覆盖了一个模块的语言特性，能照抄能用 |
| 8 | 覆盖多语言机制（生命周期/错误模型/泛型/IO/编码），**踩过的坑有实测记录** |
| 10 | 8 分 + 能**反推标准条文**（为什么 UB、为什么实现定义），并把经验迁移到新场景 |

## 4. 校准：同一个分数在三种视角下的含义

| 视角 | 含义 |
|---|---|
| 学习项目 | 77 分 ≈ 前 10%（不变式意识 + 实测记录 + 验收清单三样同时具备的人很少） |
| 作品集 | 已可拿出手，但缺 README、招牌功能没接线，面试深问会露 |
| 敢存真数据的产品 | **还不行**：两条静默坏数据路径 + 存储层 0 测试 |

定级一句话：**优秀的教学型工程，尚未达到"敢存真数据"的产品标准。**

## 6. 复核协议（下次打分照这个来）

1. **先跑证据**，再看代码：
   ```bash
   cmake --build build --config Debug && ctest -C Debug --output-on-failure
   git log --oneline -10 && git status --short
   ```
2. **逐维找证据**，写进上面那张表的"证据"列。**找不到就按 6 分以下处理。**
3. **反例自查**：每维问一句"如果我要证明它比写的更差，第一个证据是什么？"
4. 分数变化超过 ±0.5 的维度，**必须写一句原因**（做了什么 / 退步在哪）。
5. 打分日期与 commit 哈希一起记录，保证可回溯。
