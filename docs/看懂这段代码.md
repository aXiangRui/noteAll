# 看懂这段代码 —— 从 `loadGraph` 到 `Runner` 的最短路径

> 目标：**只讲能让你动手改代码的部分**，不讲实现细节。
> 读完大约 15 分钟；看不懂的段落直接跳过，不影响你写 `Runner`。

---

## 0. 你只需要看懂三件事

| 东西 | 一句话 | 文件 |
|---|---|---|
| `Node` 是**数据** | `id` + `type` + `config`，从 JSON 读出来，里面没有一行"执行代码" | `workflow/node.hpp` |
| `NodeRegistry` 是**一张表** | `type → 函数`。引擎拿到节点，查表得到该调哪个函数 | `workflow/node_registry.hpp` |
| `Runner` 是**遍历 + 插值** | 按拓扑序走一遍：把 `{{ }}` 换成真值 → 查表调函数 → 结果存进上下文 | `workflow/engine.hpp` |

记住这三句，后面全是细节。

## 1. 四个 C++ 特性（各 3 行）

这四样你眼熟之后，仓库里 80% 的陌生语法就消失了。

### `std::expected` —— 要么有值，要么有错误（不抛异常）

```cpp
std::expected<int, std::string> parse(std::string_view s);   // 成功给 int，失败给 string

if (auto r = parse("42")) { use(*r); }        // 有值：*r
else                     { log(r.error()); }  // 出错：r.error()
```

你在代码里看到所有 `std::expected<T, X>` 都是这个意思。

### `std::variant` —— "这几个类型之一"

```cpp
using NodeConfig = std::variant<InputConfig, LlmConfig, JsonConfig, IfConfig, OutputConfig>;

NodeConfig config = LlmConfig{ .model = "deepseek-chat" };   // 现在装的是 LlmConfig
auto* llm = std::get_if<LlmConfig>(&config);                  // 装错了就得到 nullptr，不抛
```

> 坑：`NodeConfig config;` 默认装的是**第一个备选**（`InputConfig`）。
> 所以 `Node` 的 `type` 默认也是 `Input` —— 两者默认是对上的。

### `std::function` —— 把函数当值存起来

```cpp
using NodeHandler = std::function<std::expected<Value, NodeError>(Node const&, RunContext const&)>;

registry.add(NodeType::Llm, makeLlmHandler(*chat));   // 把"一个函数"存进表
```

`std::function` **只出现在表里**，绝不出现在 `Node` 里 —— 那正是"节点是数据"的意思。

### `nlohmann::json` —— 像字典一样读写

```cpp
Value v = Value{{"text", "你好"}};   // 造一个对象
v["text"];                           // 取值
v.dump();                            // 转成字符串
Value::parse(text);                  // 解析（会抛异常，所以外面要 try/catch）
```

`workflow::Value` 就是 `nlohmann::json` 的别名。

## 2. 一条完整调用链

```
flows/draft.json
      │  loadGraph()
      ▼
   Graph { nodes: [Node, Node, ...] }
      │  validate()      重复 id / 悬空边 / 无 input / 有环
      │  topoOrder()     → ["in", "llm", "parse", "out"]
      ▼
   Runner::run()
      └─ 按 order 逐个节点：
           1) 取出 Node（要**拷贝**一份，别改原图）
           2) interpolate("{{ in.raw_text }}") → 真实字符串
           3) registry.find(node.type) → 找到处理器
           4) 调用：handler(节点副本, 上下文) → Value 或 NodeError
           5) context.set(node.id, value)      ← 下游就能引用 {{ llm.text }}
           6) traces 里记一条（id / 成功失败 / 耗时）
```

**关键点**：第 5 步是变量流动的全部秘密。节点只负责"吐出自己的结果"，
引擎负责"把它按 id 存进上下文"，下游用 `{{ llm.text }}` 取 —— 节点之间**从不直接传值**。

## 3. 一次真实运行，数据长什么样

图（`flows/draft.json` 的节点部分）：

```json
[
  { "id": "in",    "type": "input",  "fields": ["raw_text"] },
  { "id": "llm",   "type": "llm",    "model": "deepseek-chat",
    "prompt": "把这段整理成 JSON：{{ in.raw_text }}" },
  { "id": "parse", "type": "json",   "input": "{{ llm.text }}" },
  { "id": "out",   "type": "output", "value": "{{ parse.json.summary }}" }
]
```

| 时刻 | `RunContext` 里有什么 | 插值结果 |
|---|---|---|
| 开始 | `in = { "raw_text": "下午跟老张聊排期" }` | — |
| 跑到 `llm` | 同上 | prompt = `把这段整理成 JSON：下午跟老张聊排期` |
| `llm` 成功 | `+ llm = { "text": "{\"summary\":\"与老张确认排期\"}" }` | — |
| 跑到 `parse` | 同上 | input = `{"summary":"与老张确认排期"}` |
| `parse` 成功 | `+ parse = { "json": { "summary": "与老张确认排期" } }` | — |
| 跑到 `out` | 同上 | value = `与老张确认排期` ← 这就是最终输出 |

注意 `llm` 节点的输出是 `{"text": "..."}` 这种**对象**，所以下游要写 `{{ llm.text }}`；
如果处理器直接返回字符串 `"..."`，那写 `{{ llm }}` 就行。

## 5. 建议的阅读顺序（15 分钟）

1. `include/workflow/node.hpp` —— 60 行，认清"节点是数据"
2. `include/workflow/node_registry.hpp` —— 30 行，认清"执行函数在表里"
3. `include/workflow/graph.hpp` 里 `topoOrder` 上方那 10 行注释 —— 认清"顺序从哪来"
4. `include/workflow/engine.hpp` 顶部那 10 行 —— 你要写的五步
5. 然后打开 `src/workflow/engine.cpp`，开始写第一版

**第一版别追求通用**：

- 插值先只处理 `prompt` / `value` / `input` 这三个字段（别写通用 visitor）
- 失败先只做 `stopOnError`
- `if` 节点先跳过（返回 `skipped`），等基础链路跑通再加

跑通 `input → output` 就算赢。
